# Routing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Units start at a tier chosen by a deterministic router, climb a `trivial → standard → complex → top` ladder on red attempts, and fall back to another provider (with an in-memory cooldown) when their provider is rate limited.

**Architecture:** A pure `routeTier` and the `Rung` type live in `packages/core`. The ledger's `AttemptInfo` widens (`tier` may be `top`, plus optional `routed` and `fallback_for`). The engine derives each unit's rung from the ledger (`unitHistory`: start tier from the first attempt's `routed`, count of red attempts) and recomputes the route every attempt inside `runUnit`; a per-build cooldown map swaps in the role's `fallback` route.

**Tech Stack:** TypeScript on Bun, zod, `bun test`.

**Spec:** `docs/superpowers/specs/2026-11-06-routing-design.md`

## Global Constraints

- A config with no `top` and no `fallback` behaves as before, apart from the router's start tier.
- `Rung = "trivial" | "standard" | "complex" | "top"`; a role without a `top` route is capped at `complex`.
- `blocked`, `error` and `interrupted` attempts never add a rung; only `red` does. Rate-limited attempts never count.
- Cooldown is in memory per build, default 60 000 ms when the worker gives no `retry_after`.
- The rung is never stored: start tier comes from the ledger (`routed` on the unit's first attempt since the latest plan), reds are counted from the ledger.
- No attribution of any kind in commit messages (project CLAUDE.md overrides any harness reminder).
- `bun test <path>` per task; baseline note: ~70 tests in `packages/cli` and `packages/engine` (daemon, native sandbox, landing) fail in the agent sandbox before this work; compare against a baseline checkout, do not chase them.

## Review Focus

- A build resumed after a crash (attempt 2 red) must continue at the same rung as an uninterrupted run. (Task 4)
- A role with no `top`, no `fallback` (planner, documenter, old configs): no behavior change, no throw. (Tasks 1, 4)
- A fallback on the same provider as the primary, or also cooling: ignored, the run pauses as today. (Task 5)
- A rate limit with no `retry_after`: cooldown of 60 s, checked with an injected clock, not real time. (Task 5)
- A unit whose scope matches 0 files (all new) or more than 20 files: signals stay finite and no more than 20 files are read. (Tasks 2, 4)

### Task 2: The start-tier router

**Files:**
- Modify: `packages/core/src/router.ts`
- Test: `packages/core/test/router.test.ts`

**Interfaces:**
- Consumes: `Task`, `Complexity` from `schemas/plan.ts`.
- Produces: `export type RouteSignals = { files: number; lines: number; criteria: number; crossProject: boolean; planner: Complexity }` and `export function routeTier(task: Task, signals: RouteSignals, complexScopeGlobs = 5): { tier: Complexity; score: number; reasons: string[] }`.

Rules (exact values):
- Score = `files` + `floor(lines / 100)` + `2 * criteria` + (lane is not `contained` ? 3 : 0) + (`crossProject` ? 3 : 0) + planner vote (`trivial` 0, `standard` 1, `complex` 3) − (task kind `docs` ? 2 : 0), floored at 0.
- Base tier from score: `trivial` when score ≤ 4 **and** the trivial qualifier holds (lane `contained`, `files` ≤ 2, `lines` ≤ 150, `criteria` ≤ 1, not `crossProject`); `standard` when score ≤ 13 (or ≤ 4 without the qualifier); `complex` when score ≥ 14.
- Floors applied after: lane `wide` or `irreversible` or `crossProject` → at least `standard`; `task.scope.length > complexScopeGlobs` → `complex`.
- `reasons` lists each non-zero term and each floor that raised the tier, e.g. `"2 files"`, `"lane wide floors at standard"`.

- [ ] **Step 1: Write failing tests** (names and assertions):
  - `1 file, 80 lines, 1 criterion, contained, planner standard → trivial, score 4` (the router goes below the planner's rating).
  - `the same but 3 files → standard` and `the same but 160 lines → standard` and `the same but lane wide → standard, reasons mention the floor`.
  - `2 files, 120 lines, 1 criterion, planner standard → standard, score 6`.
  - `5 files, 500 lines, 3 criteria, planner standard → complex, score 17`.
  - `crossProject → at least standard even at score 0`.
  - `6 scope globs → complex`.
  - `0 files and 0 lines (all new files) with 1 criterion → trivial`.
  - `kind docs lowers the score by 2 and never below 0`.
- [ ] **Step 2: Run** `bun test packages/core/test/router.test.ts` → fails (`routeTier` not defined).
- [ ] **Step 3: Implement** `routeTier` as specified.
- [ ] **Step 4: Run** → pass. **Step 5: Commit** `core: routeTier, the start-tier router`.

### Task 5: Fallback provider with cooldown

**Files:**
- Modify: `packages/engine/src/engine.ts` (`Ctx`, `build()` context construction, the `interrupted` branch of `runUnit`)
- Modify: `packages/engine/src/config.ts` (add `fallbackRoute`)
- Test: `packages/engine/test/engine.test.ts`, `packages/engine/test/resume.test.ts`

**Interfaces:**
- Consumes: `resolveRoute`, `providerOf` (engine config), `RunPlanOptions`.
- Produces: `RunPlanOptions.now?: () => number` (default `Date.now`); `Ctx.cooldown: Map<string, number>` (provider → epoch ms until which it is cooling), created once per `build()`; `fallbackRoute(config: EngineConfig, role: string): Route | undefined` returning `config.routing[role]?.fallback`; the 60 000 ms constant `DEFAULT_COOLDOWN_MS`.

Behavior: at the start of each attempt, if the ladder route's provider is cooling (`cooldown.get(p) > now()`) and `fallbackRoute` exists with a different provider that is not cooling, use it and set `fallback_for` to the primary provider on the attempt's `info`. On a `rate_limit` interruption: set `cooldown[provider of the attempt's route] = retryAfter parsed as epoch ms, else now() + DEFAULT_COOLDOWN_MS`; append `unit.attempt.interrupted` as today; if a usable fallback exists now, do not return: `used--` and continue the loop (the attempt number still advances, the interrupted attempt does not count); otherwise return `paused` as today.

- [ ] **Step 1: Write failing tests** with a scripted worker returning `rate_limited` for the primary model and `ok` for the fallback model, and an injected `now`:
  - A rate-limited first attempt with a configured fallback on another provider: the unit finishes green, two `unit.attempt.started` events exist, the second has the fallback's model and `fallback_for` set, the first attempt is `interrupted`, and the run did not pause.
  - A second unit starting while the primary is cooling goes straight to the fallback (no attempt on the primary).
  - After advancing `now` past the cooldown, a new unit uses the primary again.
  - No `fallback` configured: the run pauses with `rate_limit` exactly as before (the existing rate-limit tests stay green).
  - Fallback on the same provider as the primary: ignored, the run pauses.
  - Fallback provider also cooling (set by an earlier 429 on it): the run pauses.
  - No `retry_after` from the worker: the cooldown lasts `DEFAULT_COOLDOWN_MS` (advance `now` by 59 999 → still cooling; 60 000 → not).
- [ ] **Step 2: Run** the engine tests → the new tests fail.
- [ ] **Step 3: Implement** as described; `unit.attempt.interrupted` and `run.paused` writing stay where they are.
- [ ] **Step 4: Run** `bun test packages/engine/test/engine.test.ts packages/engine/test/resume.test.ts packages/engine/test/scheduler.test.ts` → pass apart from the baseline failures.
- [ ] **Step 5: Commit** `engine: fallback provider with an in-memory cooldown`.
